## 1. Correct role of research in UltraGoal

Research informs UltraGoal’s product and engineering decisions. It does not automatically create:

- a law ID;
- standards rows;
- schemas;
- red/green fixtures;
- receipts;
- setup/retrofit outputs;
- package inventory requirements;
- final-packet blockers;
- update-goal blockers; or
- durable evidence directories.

The current source-to-law authority graph is therefore superseded as a research operating model.

Use:

```text
source or product observation
→ exact decision-relevant claim
→ current product/repository evidence
→ one canonical owner
→ no-change, update, replace, or retire
→ cheapest falsifier
→ one compact decision delta
```

If the source changes no current decision, make no repository change.

## 2. Core foundations that remain current

### A. User outcome and product loop

1. **User value precedes governance expansion.**
   Sources: DORA 2025 — https://dora.dev/research/2025/dora-report/; User-centric focus — https://dora.dev/capabilities/user-centric-focus/.
   Decision: the current milestone remains one useful installed loop. Gate, receipt, document, and test counts are diagnostics, not the outcome.

2. **Use small batches and first-truth loops.**
   Source: DORA Working in Small Batches — https://dora.dev/capabilities/working-in-small-batches/.
   Decision: run current source, repair one observed product blocker, rerun, then deepen only around named risk. Do not redesign the entire governance system first.

3. **Validate the actual user/dependent-system boundary.**
   Source: Building to the Test — https://arxiv.org/abs/2606.28430; Design Judgment collector correction.
   Decision: an external evaluator owns target snapshots, failure injection, package/install identity, hidden-write detection and final `CL-USABLE-LOOP` judgment. UltraGoal does not self-certify product success.

4. **Human control must be understandable.**
   Source: Amershi et al. — https://www.microsoft.com/en-us/research/publication/guidelines-for-human-ai-interaction/.
   Decision: expose target, effect, authority, consequences, uncertainty, correction, cancellation and recovery. An approval token without comprehension is not adequate control.

### B. Repository and context engineering

5. **Map, not manual.**
   Source: OpenAI Harness Engineering — https://openai.com/index/harness-engineering/.
   Decision: root instructions route to the current goal/plan and one relevant domain module. They do not transitively load every root document, generated projection and validation artifact.

6. **Repository instructions are hypotheses, not guaranteed performance improvements.**
   Sources: https://arxiv.org/abs/2602.11988 and https://arxiv.org/abs/2607.27250.
   Decision: compare current, reduced, direct-source and relevant-module conditions on byte-identical code before adopting a context reduction.

7. **Standing prompts must be bounded.**
   Sources: OpenAI GPT-5.6 guidance — https://developers.openai.com/api/docs/guides/latest-model; Prompt-Induced Waste — https://arxiv.org/abs/2608.01347.
   Decision: remove generic exhaustive-depth, mandatory multi-approach, universal-review and broad-retry language. Preserve outcome, authority, acceptance and stop rules.

### C. Current execution state and long-running work

8. **Explicit current state is better than repeated history.**
   Source: Ledger — https://arxiv.org/abs/2608.00808.
   Decision: runtime state may track current observations, modifications and attempts. Do not mirror it in several plans, registries, receipts, backlogs and generated projections.

9. **Use one durable state owner.**
   Sources: OpenAI Symphony — https://openai.com/index/open-source-codex-orchestration-symphony/; Temporal — https://docs.temporal.io/.
   Decision: use the active plan for program-level state and runtime data for current operation state. Add durable workflow technology only for demonstrated crash/replay requirements.

10. **Effects require identity, idempotency and reconciliation.**
    Source: Temporal official durability guidance.
    Decision: preserve action/effect IDs, exact target, authorization, retry classification, ambiguous-effect reconciliation and crash/fault tests. Temporal is an optional implementation.

11. **Parallelism is earned.**
    Source: Multi-Agent Teams Hold Experts Back — https://arxiv.org/abs/2602.01011.
    Decision: one coupled lane by default. Parallel work requires independent semantic authority, disjoint writes, no peer-unmerged dependency, local oracles and reserved root integration capacity.

### D. Security, identity and supply chain

12. **Authority remains deterministic.**
    Sources: NIST AI Agent Standards Initiative — https://www.nist.gov/artificial-intelligence/ai-agent-standards-initiative; NIST identity concept — https://csrc.nist.gov/pubs/other/2026/02/05/accelerating-the-adoption-of-software-and-ai-agent/ipd.
    Status: emerging/draft, not normative.
    Decision: preserve explicit principal, repository, target, candidate, permission and effect identities. Do not claim NIST conformance.

13. **Secure development uses SSDF 1.1 as final baseline.**
    Source: https://csrc.nist.gov/pubs/sp/800/218/final.
    Decision: integrate secure preparation, protected source/build, testing, response and vulnerability handling. Treat SSDF 1.2 as provisional only.

14. **SLSA 1.2 governs provenance, not product correctness.**
    Source: https://slsa.dev/spec/v1.2/.
    Decision: bind source, build, package and install identities. Provenance cannot substitute for runtime, user outcome or security-completeness evidence.

15. **MCP and A2A are optional boundary protocols.**
    Sources: MCP 2026-07-28 — https://blog.modelcontextprotocol.io/posts/2026-07-28/; A2A 1.0 — https://a2a-protocol.org/latest/announcing-1.0/.
    Decision: UltraGoal does not need either for internal operation unless a real tool/interoperability boundary requires it. If MCP is used, apply the modern protocol-era/deprecation guidance.

### E. Observability and improvement

16. **Observe for a named question.**
    Sources: Google SRE Monitoring — https://sre.google/workbook/monitoring/; OpenTelemetry — https://opentelemetry.io/docs/specs/.
    Decision: baseline operation output includes target, candidate, effect, status, error and timing. Add richer traces/metrics/logs only where a failure, risk or current claim requires them.

17. **Keep domain state independent of telemetry.**
    Decision: run/action/effect IDs and claim state are product types. OpenTelemetry is an export/diagnostic boundary, not the source of authority.

18. **Post-deployment monitoring is an unresolved practice area.**
    Source: NIST AI 800-4 — https://doi.org/10.6028/NIST.AI.800-4.
    Decision: use its monitoring categories to ask questions; do not require a universal full local stack, source cards and receipt graph.

19. **Repeated failures should improve the earliest controllable layer.**
    Sources: OpenAI Harness Engineering, DORA and Design Judgment Authorial.
    Decision: a repeated material failure can justify a code/test/tool/schema/prose change. One incident does not automatically create a law, persona, quality receipt, hook, source obligation or backlog row.

### F. Evidence and receipt discipline

20. **Receipts preserve transitions, not activity.**
    Source: Design Judgment Authorial 11.1.
    Decision: ordinary reads, checks, diagnostics, drafts, no-ops, creator runs and reviews create no repository receipt files. Persist only authorization transitions, cross-process recovery, irreproducible external observations and release decisions.

21. **Equivalent inspectable output counts.**
    Source: Design Judgment v5 collector correction.
    Decision: the evaluator resolves valid output from actual manifests or product interfaces. Internal filename/path conformity cannot create a product failure unless the path is itself the product contract.

22. **Tests and reviewers are evidence, not authority.**
    Sources: Building to the Test, HANDBOOK.md, current judge research.
    Decision: required/prohibited final-state outcomes and deterministic controls outrank reviewer consensus, receipt shape, test count and self-report.

## 4. Replacement research lifecycle

### Step 1 — classify

For a new or changed source, record:

- current official version/date;
- status: controlling, supporting, empirical, draft, emerging or historical;
- exact decision-relevant claim;
- evidence ceiling;
- review trigger.

### Step 2 — compare against current product evidence

Ask:

- Does UltraGoal currently implement or depend on the claimed mechanism?
- Is there a demonstrated product failure or active claim affected by it?
- Is the source describing a standard, a case study, a hypothesis, or an open challenge?
- Can the decision remain unchanged?

### Step 3 — choose one disposition

```text
no_change
update_existing_owner
replace_owner
retire_surface
hold_for_product_evidence
```

### Step 4 — implement at the earliest controllable layer

Preference order:

```text
product interaction / tool contract
code or configuration
focused test or external oracle
runtime state or permission
canonical domain documentation
routed standard
```

Do not add a schema/receipt/projection merely to make the source visible.

### Step 5 — retain one compact delta

Use the shared foundation log only when a current decision changes or an important no-change decision must survive sessions. The row identifies one owner, claim ceiling and review trigger.

## 5. Claim ceilings

| Surface | Maximum claim |
|---|---|
| Research source | The source supports the exact summarized principle. |
| Code/unit/contract checks | The tested source boundary behaves as observed. |
| Product evaluator | The exact candidate completes the tested operator boundary. |
| Package/install journey | The exact bits install/discover/run in the tested host. |
| One representative repository loop | `CL-USABLE-LOOP` in that tested envelope only. |
| Repeated intended-user use | Observed Product Fitness in the sampled envelope, not universal value. |

## 6. Review triggers

Review this file when:

- the current product loop exposes a new repeated failure;
- the target/effect/autonomy envelope expands;
- MCP/A2A/OTel/SLSA/SSDF/current Rust runtime guidance changes;
- a security incident affects paths, subprocesses, credentials, package or effects;
- the context A/B shows a required rule was removed or an active rule adds no value;
- a historical registry reader is removed; or
- a source is found to be misquoted or over-operationalized.

Do not review merely because a source-card freshness timer expires.
