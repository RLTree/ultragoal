# Repo Patterns Extracted From codex-workflow-rs

This document extracts portable patterns from `codex-workflow-rs`. It intentionally separates reusable law from repo-specific facts.

## Reusable Patterns

### Compact Root Instructions

`AGENTS.md` should act as a table of contents. It should point to the standards, architecture, plans, specs, security, reliability, and design docs. It should not become a monolithic manual.

Plugin template: `templates/AGENTS.md`

### Routed Agent Standards

A compact standards router should point to semantically named standards modules
instead of becoming an always-loaded mega document. The routed modules should
cover:

- namespace law;
- coverage law;
- parse-at-boundary law;
- codemap requirements;
- progressive disclosure;
- mechanical enforcement;
- ExecPlan requirements;
- feedback loops;
- worktree law;
- review and completion law;
- standards gardening and self-improvement.

Plugin templates: `templates/AGENT_STANDARDS.md`,
`templates/agent-standards/`

### ExecPlans As Contracts

Long work should be specified as a self-contained living document. A lane must be restartable from its ExecPlan. The plan must include purpose, progress, discoveries, decisions, outcomes, context, concrete steps, validation, idempotence, recovery, and artifacts.

Plugin template: `templates/LANE_EXECPLAN.md`

### Lane Registry

`LANE_REGISTRY.json` should be the canonical lane authority. It defines lane launch readiness, parallel strategy, file ownership, dependencies, root verification phases, stale session/worktree state, blockers, and teardown. A markdown view may exist for humans, but it must not be a conflicting authority.

Plugin templates: `templates/LANE_REGISTRY.json`, `templates/LANE_REGISTRY.md`

### Root Verification Backlog

Any non-proven claim should be tracked explicitly as:

- `lane_owed`
- `root_owed`
- `externally_blocked`
- `withheld_claim`

Plugin templates: `templates/VERIFICATION_BACKLOG.json`, `templates/VERIFICATION_BACKLOG.md`

### Validation Artifacts

Every meaningful lane or final proof needs durable receipts. Receipts should identify:

- lane id;
- branch and worktree;
- commit hash;
- commands and exits;
- evidence paths and digests;
- claim ceiling;
- residual gaps;
- worktree cleanliness;
- teardown state.

Plugin authorable templates and generated receipts: `templates/COMPLETION_MANIFEST.json`, generated ready receipts such as `examples/generated/READY_FOR_MERGE.example.json`, and validator receipts under `validation_artifacts/ultragoal-audit/`

### Live Beneficial E2E

Feature completion requires using the built feature on a real helpful task. Smoke tests, fixtures, mocks, and toy examples only prove their own scope.

Plugin integration: `proof-gate` must block feature completion claims that lack live beneficial evidence.

### Worktree Hygiene

Every lane gets isolated work. Closed, merged, superseded, or abandoned worktrees must be cleaned up after artifacts are preserved. Dirty worktrees block closure.

Plugin integration: `orchestrator-reconciler` validates lane registry and worktree state.

### Generated Ready Receipts

Ready receipts should be generated by the validator. Hand-written ready receipts should be rejected because they are too easy to fake.

Plugin integration: `proof-gate` writes generated ready receipts only after validation.

## Repo-Specific Facts Not To Generalize Blindly

- Lane ids such as `0100`, `0112`, and `0121`.
- Deep Research route names.
- Downbeat product names.
- Rust-specific command names.
- The exact 250 LOC cap unless chosen as plugin default.
- The exact coverage tooling unless the target repo uses comparable tooling.
- `~/.codex/workflows` as a parity truth source.

## Generalization Rule

When turning a local practice into plugin law, ask:

1. Does it prevent a false completion, stale proof, or lane collision?
2. Can it be checked mechanically?
3. Does it improve agent legibility without crowding context?
4. Does it apply across repos, or should it be a template default?
5. Can a reviewer tell whether it passed or failed from an artifact?

If the answer is no, keep it as an example rather than law.
